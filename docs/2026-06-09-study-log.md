## SSR과 CSR을 나누는 기준

오늘 가장 중요한 기준은 아래와 같다.

```txt
처음부터 모두에게 보여야 하는 공개 콘텐츠
-> SSR 후보

사용자 행동 이후 바뀌는 인터랙션
-> CSR 후보
```

상품 상세에서는 아래처럼 나눠 생각했다.

```txt
SSR 후보
-> 상품명
-> remarks
-> tags
-> 가격
-> 판매자명
-> metadata / Open Graph

CSR 후보
-> 스크랩 버튼
-> 구매 버튼
-> 결제 모달
-> 포인트 충전
-> Swiper 이미지 상태
-> Kakao map
-> 문의 작성/삭제
```

보드 상세에서는 아래처럼 나눴다.

```txt
SSR 후보
-> 게시글 제목
-> 작성자
-> 작성일
-> 본문
-> 이미지
-> metadata / Open Graph

CSR 후보
-> 목록으로 이동
-> 수정 페이지 이동
-> 좋아요/싫어요
-> 댓글 작성
-> 댓글 목록 무한 스크롤
```

SSR은 초기 HTML에 공개 콘텐츠를 넣어 새로고침 시 바로 보이게 하고, CSR은 hydration 이후 클릭, 입력, 모달, mutation 같은 동작을 담당하게 하는 방식이 자연스럽다.

## 상품 상세 리팩토링

상품 상세는 아래 흐름으로 정리했다.

```txt
src/app/homework37/products/[productId]/page.tsx
-> 서버 컴포넌트
-> generateMetadata 연결
-> 서버에서 상품 상세 데이터 조회
-> ProductDetailServerShell 렌더링

src/components/product-detail/metadata.ts
-> 상품 상세 dynamic metadata 생성

src/components/product-detail/getData.ts
-> 상품 상세 SSR 데이터 조회

src/components/product-detail-server-shell/index.tsx
-> 서버 컴포넌트
-> 서버 summary를 만들고 client shell에 slot으로 전달

src/components/product-detail-client-shell/index.tsx
-> 클라이언트 컴포넌트
-> useProductDetailHook 실행
-> state, event, mutation 연결

src/components/product-detail/index.tsx
-> ProductDetailView
-> 실제 상세 UI 마크업
```

핵심 구조는 아래와 같다.

```tsx
<ProductDetailClientShell
  productData={productData}
  summary={<ProductDetailSummaryComponent data={productData} />}
/>
```

`ProductDetailSummaryComponent`는 서버 shell에서 import하고, client shell에는 `summary` prop으로 넘긴다.

중요한 점은 client shell이 서버 summary를 직접 import하지 않는다는 것이다.

```txt
나쁜 흐름
-> client component가 server summary를 직접 import
-> summary도 client 쪽으로 끌려갈 수 있음

좋은 흐름
-> server shell이 server summary를 생성
-> client shell은 ReactNode slot으로 받음
```

이 방식 덕분에 클라이언트 컴포넌트가 필요한 이벤트와 상태를 유지하면서도, 읽기 전용 일부 UI는 서버 컴포넌트로 남길 수 있다.

## Apollo cache와 SSR props

오늘 가장 헷갈렸던 부분은 Apollo cache와 SSR props의 관계였다.

처음에는 서버에서 Apollo로 데이터를 가져와 클라이언트 컴포넌트에 props로 넘기면, 클라이언트 Apollo cache도 그 값을 알 것처럼 느껴졌다.

하지만 실제로는 그렇지 않다.

```txt
서버 Apollo query
-> 서버 Apollo cache 또는 서버 응답 데이터
-> React props로 클라이언트 컴포넌트에 전달

클라이언트 Apollo cache
-> ApolloProvider 아래 useQuery/useMutation/cache.modify에서 사용하는 별도 cache
```

서버에서 내려준 데이터는 클라이언트 Apollo cache에 자동으로 들어가지 않는다.

따라서 화면이 SSR props를 보고 있으면, 클라이언트에서 `cache.modify`를 해도 화면이 자동 갱신되지 않는다.

```txt
useQuery data를 보는 화면
-> Apollo cache 변경을 구독
-> cache.modify 후 UI 갱신 가능

SSR props를 보는 화면
-> Apollo cache를 구독하지 않음
-> cache.modify 후 UI 갱신 안 됨
```

이 차이 때문에 보드 상세의 좋아요/싫어요는 client state로 관리하는 쪽이 자연스럽다고 판단했다.

```txt
초기값
-> SSR props

클릭 직후 값
-> client state

서버 확정값
-> mutation response
```

좋아요 mutation 응답은 아래처럼 내려왔다.

```json
{
  "data": {
    "likeBoard": 9
  }
}
```

따라서 state를 갱신할 때는 `result.data.likeCount`가 아니라 `result.data.likeBoard`를 읽어야 한다.

`likeCount`는 화면 state 이름이고, `likeBoard`는 GraphQL mutation 응답 필드 이름이다.

이 차이를 놓쳐서 `undefined + 1`이 되고, React에서 `NaN` children 경고가 발생하기도 했다.

## 서버 Apollo Client와 캐시

서버에서 Apollo Client를 싱글톤으로 만들면 `InMemoryCache`가 이전 요청의 값을 들고 있을 수 있다.

기존 방식은 아래와 비슷했다.

```ts
export const serverApolloClient = new ApolloClient({
  cache: new InMemoryCache(),
  link: new HttpLink({ uri: "..." }),
  ssrMode: true,
});
```

이 방식은 모듈이 로드될 때 Apollo Client가 한 번 만들어지고, 이후 서버 조회에서 같은 client/cache를 재사용할 수 있다.

오늘은 이를 함수 방식으로 바꿨다.

```ts
export function createServerApolloClient() {
  return new ApolloClient({
    link: new HttpLink({
      uri: "https://main-practice.codebootcamp.co.kr/graphql",
      fetchOptions: {
        cache: "no-store",
      },
    }),
    cache: new InMemoryCache(),
    ssrMode: true,
  });
}
```

이렇게 하면 호출할 때마다 새 Apollo Client와 새 `InMemoryCache`를 만들 수 있다.

또한 `fetchOptions: { cache: "no-store" }`를 넣었을 때 새로고침 후 서버 데이터 최신성이 더 나아지는 것을 확인했다.

오늘 정리한 구분은 아래와 같다.

```txt
createServerApolloClient()
-> 서버 Apollo InMemoryCache 공유 문제를 줄임

fetchOptions: { cache: "no-store" }
-> Apollo HttpLink 내부 fetch가 캐시된 응답을 쓰지 않도록 함

fetchPolicy: "no-cache"
-> 특정 Apollo query가 Apollo cache를 읽거나 저장하지 않도록 함
```

최신성이 중요한 데이터와 캐시 이점이 중요한 데이터는 다르게 판단해야 한다.

```txt
좋아요 수, 싫어요 수, 댓글 수, 재고, 구매 가능 상태
-> 최신성이 중요

게시글 제목, 본문, 작성자, 상품 설명
-> 캐시 가능성을 검토할 수 있음
```

## REST API였다면

REST API를 사용해도 SSR/CSR 분리 개념은 같다.

차이는 데이터 요청 도구다.

```txt
GraphQL/Apollo SSR
-> serverApolloClient.query()

REST SSR
-> fetch(url, { cache: "no-store" })

GraphQL/Apollo mutation
-> useMutation

REST mutation
-> fetch(url, { method: "POST" })
```

REST 방식에서는 Apollo cache 문제가 줄어드는 대신, optimistic update와 실패 시 rollback을 직접 state로 관리해야 한다.

예를 들면 좋아요는 아래 흐름이 된다.

```ts
const prevLikeCount = likeCount;

setLikeCount((prev) => prev + 1);

try {
  const response = await fetch(`/api/boards/${boardId}/like`, {
    method: "POST",
  });

  const result = await response.json();
  setLikeCount(result.likeCount);
} catch {
  setLikeCount(prevLikeCount);
}
```

즉 REST든 GraphQL이든 핵심은 같다.

```txt
초기 데이터는 서버
사용자 행동 이후 바뀌는 값은 클라이언트 상태
```

## 과도한 추상화에 대한 판단

SSR을 활용하려고 모든 UI를 잘게 쪼개는 것이 항상 좋은 것은 아니다.

오늘 정리한 기준은 아래와 같다.

```txt
나눌 가치가 있는 것
-> 공개 읽기 데이터
-> 초기 HTML에 있으면 좋은 큰 콘텐츠 블록
-> SEO/OG에 필요한 정보
-> 이벤트가 없는 의미 있는 UI 묶음

굳이 나누지 않아도 되는 것
-> 한두 줄짜리 텍스트
-> 이벤트와 강하게 섞인 영역
-> 파일만 늘고 이해가 어려워지는 영역
```

상품명 하나, 가격 하나처럼 너무 작은 단위로 서버 컴포넌트를 만드는 것은 과도할 수 있다.

대신 아래처럼 의미 있는 블록 단위로 나누는 편이 좋다.

```txt
ProductDetailSummary
BoardDetailHeader
BoardArticle
SellerInfo
```

서버 컴포넌트화 자체가 목적이 되면 구조가 복잡해진다.

SSR의 목적은 초기 노출 가치가 있는 공개 콘텐츠를 서버에서 준비하는 것이다.

## 오늘 기억할 점

오늘의 핵심은 아래 문장으로 정리할 수 있다.

```txt
SSR은 초기 화면과 공개 데이터를 책임지고,
CSR은 사용자 행동 이후 바뀌는 상태를 책임진다.
```

그리고 SSR과 CSR을 섞을 때 가장 중요한 것은 데이터 소유권이다.

```txt
이 데이터는 서버 props가 소유하는가?
이 데이터는 client state가 소유하는가?
이 데이터는 Apollo cache가 소유하는가?
```

이 질문을 먼저 정해야 UI 갱신과 캐시 동기화가 덜 꼬인다.

오늘 만든 폴더와 파일은 학습 과정에서 다소 복잡해졌지만, 직접 구조를 만들면서 아래 내용을 체감했다.

```txt
page.tsx
-> route entry와 서버 조립

metadata.ts
-> dynamic metadata 생성

getData.ts
-> 서버 데이터 조회

ServerShell
-> 서버 컴포넌트 조각을 만들고 client shell에 전달

ClientShell
-> hook, state, event, mutation 연결

View
-> UI 마크업
```

모든 숙제가 끝난 뒤에는 폴더 구조, 네이밍, 타입, fallback, 불필요 로그를 한 번에 정리하는 것이 좋다.
