# 2026-06-12 스터디 일지

## 오늘의 주제

어제 AWS EC2에 Next.js 앱을 직접 배포한 흐름에 이어, 오늘은 Docker로 배포 환경을 포장하는 과정을 학습했다.

핵심은 단순히 `Dockerfile`을 작성하는 것이 아니라, Next.js 앱이 실행되기 전에 필요한 파일과 컨테이너 안에 들어가면 안 되는 파일을 구분하는 것이었다.

## Docker를 이해한 방식

Docker는 코드를 담는 도구라기보다, 코드가 실행되기 위한 환경 전체를 재현하는 도구에 가깝다.

이번 스터디에서 정리한 핵심 질문은 다음과 같다.

```txt
내 앱이 실행되기 전에 필요한 파일은 무엇인가?
컨테이너 안에 들어가면 안 되는 파일은 무엇인가?
실행 환경이 매번 같은가?
```

이 세 질문을 기준으로 Dockerfile을 읽으면, 단순히 강의 코드를 따라 쓰는 것보다 훨씬 이해하기 쉬웠다.

## 이미지와 컨테이너

Docker에서 자주 헷갈리는 개념은 이미지와 컨테이너다.

- 이미지: 실행 가능한 앱 템플릿
- 컨테이너: 이미지를 실제로 실행한 프로세스

즉 Dockerfile은 이미지를 만들기 위한 설명서이고, 컨테이너는 그 이미지가 실제로 실행된 상태다.

```txt
Dockerfile
-> Docker image
-> Docker container
```

## 현재 Dockerfile 구조

현재 Dockerfile은 다음 흐름으로 구성했다.

```dockerfile
FROM node:22
WORKDIR /my-trip
COPY package.json package-lock.json ./
COPY src/dataconnect-generated ./src/dataconnect-generated
RUN npm ci
COPY . .
RUN npm run build
CMD ["npm", "run", "start"]
```

각 단계의 의미는 다음과 같다.

### 1. Node 환경 선택

```dockerfile
FROM node:22
```

Node.js가 설치된 공식 이미지를 기반으로 컨테이너 환경을 만든다.

Next.js 14는 Node 20에서도 동작하지만, 현재 프로젝트 의존성 중 Node 22를 요구하는 패키지가 있어 Node 22를 사용했다.

### 2. 작업 폴더 설정

```dockerfile
WORKDIR /my-trip
```

컨테이너 안에서 명령어를 실행할 기준 폴더를 지정한다.

### 3. package 파일 먼저 복사

```dockerfile
COPY package.json package-lock.json ./
```

의존성 설치에 필요한 파일을 먼저 복사한다.

이렇게 하면 소스 코드만 바뀐 경우 `npm ci` 단계의 Docker 캐시를 재사용할 수 있다.

### 4. 로컬 file 의존성 먼저 복사

```dockerfile
COPY src/dataconnect-generated ./src/dataconnect-generated
```

현재 프로젝트에는 다음 의존성이 있다.

```json
"@dataconnect/generated": "file:src/dataconnect-generated"
```

이 의존성은 npm registry에서 받는 패키지가 아니라 프로젝트 안의 로컬 폴더를 패키지처럼 참조한다.

따라서 `npm ci`를 실행하기 전에 `src/dataconnect-generated` 폴더도 컨테이너 안에 있어야 한다.

강의 예제와 달라진 가장 큰 이유가 바로 이 부분이었다.

### 5. 의존성 설치

```dockerfile
RUN npm ci
```

`package-lock.json` 기준으로 의존성을 정확히 설치한다.

학습용으로는 `npm install`도 가능하지만, 배포나 CI 환경에서는 `npm ci`가 더 재현성이 좋다.

### 6. 실제 소스 복사

```dockerfile
COPY . .
```

의존성 설치가 끝난 뒤 앱 소스 전체를 복사한다.

이때 `.dockerignore`에 적힌 파일들은 제외된다.

### 7. Next.js 빌드

```dockerfile
RUN npm run build
```

컨테이너 안에서 Next.js 프로덕션 빌드를 실행한다.

### 8. 컨테이너 시작 명령

```dockerfile
CMD ["npm", "run", "start"]
```

컨테이너가 실행될 때 `package.json`의 `start` 스크립트를 실행한다.

현재 `start`는 다음과 연결된다.

```json
"start": "next start"
```

즉 컨테이너가 시작되면 빌드된 `.next` 결과물을 기준으로 Next.js 프로덕션 서버가 실행된다.

배열 형태로 쓰는 이유는 Docker가 명령어를 더 명확하게 실행하고 종료 신호를 더 안정적으로 전달할 수 있기 때문이다.

## .dockerignore의 역할

`COPY . .`는 현재 폴더 전체를 컨테이너 안으로 복사한다.

그런데 로컬에는 컨테이너 안에 들어가면 안 되거나, 들어갈 필요가 없는 파일들이 있다.

```txt
node_modules
.next
.git
.env
screenshots
docs
```

이런 파일을 그대로 이미지에 넣으면 다음 문제가 생길 수 있다.

- 이미지 크기가 커진다.
- 로컬 `node_modules`가 컨테이너 의존성과 섞인다.
- 로컬 `.next` 빌드 결과가 컨테이너 빌드 결과와 섞인다.
- `.env` 같은 민감 정보가 이미지에 들어갈 수 있다.

그래서 `.dockerignore`로 제외했다.

```dockerignore
node_modules
.next
.git
Dockerfile*
docker-compose.yaml
npm-debug.log
screenshots
docs
.env
```

실무적으로도 `.dockerignore`는 매우 중요하다. Docker 빌드 문제 중 일부는 로컬 찌꺼기가 이미지에 들어가서 발생할 수 있다.

## docker-compose.yaml

현재 compose 설정은 다음 흐름이다.

```yaml
services:
  mytrip:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "2500:3000"
```

의미는 다음과 같다.

- 현재 폴더를 Docker 빌드 컨텍스트로 사용한다.
- `Dockerfile`을 기준으로 이미지를 만든다.
- 내 컴퓨터의 `2500`번 포트를 컨테이너의 `3000`번 포트에 연결한다.

따라서 브라우저에서는 다음 주소로 접속한다.

```txt
http://localhost:2500
```

컨테이너 안에서는 Next 서버가 3000번으로 실행되지만, 외부에서는 2500번으로 접근하는 구조다.

## 개발용 Docker와 배포용 Docker

Docker라고 해서 코드 수정이 자동으로 반영되는 것은 아니다.

자동 반영은 보통 개발용 compose에서 `volumes`로 로컬 폴더를 컨테이너에 연결하고, `npm run dev`로 실행할 때 가능하다.

개발용 예시:

```yaml
volumes:
  - .:/my-trip
command: npm run dev
```

반면 현재 Dockerfile은 배포용에 가깝다.

```dockerfile
COPY . .
RUN npm run build
CMD ["npm", "run", "start"]
```

이 구조에서는 코드가 바뀌면 이미지를 다시 빌드해야 한다.

```bash
docker compose up --build
```

백그라운드로 실행하려면 다음처럼 실행한다.

```bash
docker compose up --build -d
```

## Git과 Docker 배포 흐름

Docker가 자동으로 GitHub의 최신 코드를 가져오는 것은 아니다.

수동 배포에서는 다음 흐름이 자연스럽다.

```txt
로컬에서 코드 수정
-> git commit
-> git push
-> 서버에서 git pull
-> docker compose up --build -d
```

즉 서버에 새 코드를 반영하려면 다음 명령을 자주 사용하게 된다.

```bash
git pull
docker compose up --build -d
```

실무형 자동 배포에서는 이 과정을 GitHub Actions나 Jenkins 같은 CI/CD 도구가 대신한다.

```txt
main 브랜치에 merge
-> CI/CD 실행
-> 테스트
-> 빌드
-> Docker 이미지 생성
-> 서버 배포
```

## GitHub Actions 개념

GitHub Actions는 GitHub 저장소에 붙어 있는 자동화 도구다.

Jenkins를 써본 경험과 비교하면 다음처럼 이해할 수 있다.

```txt
Jenkinsfile = .github/workflows/*.yml
Jenkins job = GitHub Actions workflow
Jenkins agent = runs-on: ubuntu-latest
Build steps = steps
Webhook = on: push / pull_request
Credentials = GitHub Secrets
```

GitHub Actions를 쓰는 팀이라면 보통 특정 브랜치에 merge되었을 때 자동으로 테스트, 빌드, 배포가 실행된다.

운영 배포에서는 PR approve와 deployment approve를 나눌 수도 있다.

- PR approve: 코드를 merge해도 된다는 승인
- Deployment approve: 운영 환경에 배포해도 된다는 승인

## 오늘 정리한 핵심

- Docker는 프론트엔드 서버를 같은 환경에서 실행할 수 있게 포장하는 도구다.
- Dockerfile은 외워서 쓰기보다 설치와 실행에 필요한 파일 순서를 이해해야 한다.
- `file:` 로컬 의존성이 있으면 `npm ci` 전에 해당 폴더를 먼저 복사해야 한다.
- `.dockerignore`는 이미지 크기와 빌드 안정성, 보안 측면에서 중요하다.
- `CMD ["npm", "run", "start"]`는 컨테이너 시작 시 Next 프로덕션 서버를 실행한다는 뜻이다.
- 개발용 Docker는 volume과 dev server를 사용하고, 배포용 Docker는 build 후 start하는 구조가 일반적이다.
- 수정한 코드는 최종적으로 Git에 올리고, 서버에서는 `git pull` 후 Docker 이미지를 다시 빌드해 반영한다.
- CI/CD를 쓰면 이 수동 배포 흐름을 GitHub Actions나 Jenkins가 자동으로 대신한다.
